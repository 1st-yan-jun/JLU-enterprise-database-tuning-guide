## 0. 实验前环境准备与核心理论体系（紧扣 Unit 8 课件重点）

### 0.1 DB2 锁机制体系与层次锁架构（行锁、表锁与意向锁 IS/IX）

在《企业级数据库性能调优》Unit 8 中，并发控制（Concurrency Control）是保障数据库 ACID 事务特性的核心基石。为了平衡**数据一致性**与**系统并发吞吐量**，DB2 实现了精细的**多粒度层次锁架构（Hierarchical Locking）**：

1. **锁粒度（Lock Granularity）**：
   - **表锁（Table Lock）**：开销小（只需管理一个锁结构），但并发度极低，容易阻塞对全表的并发访问。
   - **行锁（Row Lock）**：并发度最高（不同事务可并发修改同一张表的不同行），但当并发事务量庞大时，锁内存消耗较大。
2. **意向锁机制（Intent Locks）的必要性**：
   - 如果系统仅有行锁，当事务 A 修改某一行持有行 X 锁时，事务 B 若想对整表加表级共享锁（S）或排他锁（X），数据库必须遍历整张表中的数百万行数据去检查是否存在行级冲突，开销不可承受！
   - 为解决该问题，DB2 规定：**任何事务在对某一行加行级锁（S 或 X）之前，必须首先在其所属的表上加上对应的“意向锁”（IS 或 IX）**！
   - **意向共享锁（IS, Intent Share）**：声明该事务打算读取表中的某些行（获取行级 S 锁）。
   - **意向排他锁（IX, Intent Exclusive）**：声明该事务打算修改表中的某些行（获取行级 X 锁）。
   - **效果**：其他事务若想申请表级 X 锁或 S 锁，只需在表级别检查是否已存在 IX/IS 锁即可瞬间判断冲突，极大提升了锁管理效率！

### 0.2 锁兼容性矩阵与并发冲突机理

DB2 内部维护着严格的锁兼容性矩阵（Lock Compatibility Matrix）。两个事务对同一对象申请锁时的兼容关系如下：

| 已持有模式 \ 申请模式 | IS (意向共享)  | IX (意向排他)  | S (共享锁)    | SIX (共享意向排他) | X (排他锁)    |
|:------------ |:----------:|:----------:|:----------:|:------------:|:----------:|
| **IS**       | **兼容**     | **兼容**     | **兼容**     | **兼容**       | 不兼容 (Wait) |
| **IX**       | **兼容**     | **兼容**     | 不兼容 (Wait) | 不兼容 (Wait)   | 不兼容 (Wait) |
| **S**        | **兼容**     | 不兼容 (Wait) | **兼容**     | 不兼容 (Wait)   | 不兼容 (Wait) |
| **SIX**      | **兼容**     | 不兼容 (Wait) | 不兼容 (Wait) | 不兼容 (Wait)   | 不兼容 (Wait) |
| **X**        | 不兼容 (Wait) | 不兼容 (Wait) | 不兼容 (Wait) | 不兼容 (Wait)   | 不兼容 (Wait) |

- **核心结论 1**：行级 **X 锁（排他锁）** 具有排他独占性，与任何其他行级锁（S 锁、X 锁）均不兼容！
- **核心结论 2**：表级 **IX 锁** 与另一个事务的表级 **IX 锁** 是相互兼容的（两个事务可以并发更新同一张表的不同行）；但表级 **IX 锁** 与表级 **S 锁** 不兼容。

### 0.3 四大事务隔离级别（UR, CS, RS, RR）加锁深度剖析

事务隔离级别决定了读操作获取锁的时机、锁的类型以及锁保持的时长：

1. **未落实读（UR, Uncommitted Read）**：
   - 读操作不申请任何行锁，不被任何行级 X 锁阻塞。可能发生**脏读（Dirty Read）**、不可重复读和幻读。
2. **游标稳定性（CS, Cursor Stability，DB2 默认隔离级别）**：
   - 应用程序读取某一行时获取行级 S 锁；当游标移动到下一行时，**立即释放上一行的 S 锁**！
   - **特点**：如果读操作检索的目标行当前被其他事务持有 X 锁，CS 级别会发生锁等待（Lock Wait）；但一旦读取完毕游标移走，S 锁即被释放，不再阻碍后续其他事务修改。
3. **读稳定性（RS, Read Stability）**：
   - 事务检索到的所有满足条件的行均被加上行级 S 锁，并**保持至事务结束（COMMIT/ROLLBACK）**！防止了不可重复读，但允许幻读（其他事务可插入新行）。
4. **可重复读（RR, Repeatable Read）**：
   - 事务扫描评估过的所有行（包括未满足条件的行及可能插入的新行范围）全部被加上 S 锁，并**保持至整个事务结束**！彻底杜绝不可重复读与幻读，但并发度最低，极易引发锁争用与死锁。

### 0.4 快照监视器（Snapshot Monitor）与监视器开关原理

DB2 的快照监视器可以在不中断生产业务的前提下，采样捕获数据库引擎内部实时的运行状态：

- **监视器开关（Monitor Switches）**：为了降低监控开销，DB2 将监视指标分组（如 `LOCK`、`UOW`、`BUFFERPOOL`、`TABLE`、`STATEMENT` 等）。默认情况下，涉及高频事件开销的开关处于 `OFF` 状态。
- **获取快照**：
  - `db2 get snapshot for locks on <dbname>`：获取当前数据库所有持锁与等锁的快照详情。
  - `db2 get snapshot for applications on <dbname>`：获取当前连接的所有应用程序的运行状态与 UOW 完成状态。
- **动态开关**：使用 `db2 update monitor switches using lock on uow on` 可以在会话层动态开启针对锁和工作单元的详细跟踪。

### 0.5 锁超时机制（LOCKTIMEOUT 参数与 SQL0911N 原因码 68）

- **默认行为**：DB2 数据库配置参数 `LOCKTIMEOUT` 默认值为 `-1`。这意味着如果发生锁冲突，请求锁的事务将**无限期挂起等待**，直到持有锁的事务显式提交或回滚！
- **生产隐患**：如果某个客户端事务因网络异常挂起或用户忘记提交，将导致大量后续事务被连锁阻塞，引发“雪崩效应”！
- **超时保护**：将 `LOCKTIMEOUT` 设置为具体的数值（例如 `90` 秒）。当事务等待锁的时间超过该阈值时，DB2 自动中断该请求，**强制回滚当前事务**并返回错误：
  
  ```text
  SQL0911N 因为死锁或超时，当前事务已回滚。原因码 "68"。
  (SQL0911N The current transaction has been rolled back because of a deadlock or timeout. Reason code "68".)
  ```
- **核心特征**：锁超时是**单向等待**（事务 A 等待事务 B，事务 B 并没有在等待事务 A），由计时器被动触发。

---

### 0.6 死锁检测机制（DLCHKTIME 参数、死锁检测器与 SQL0911N 原因码 2）

- **死锁成因**：两个或多个事务互相持有对方所需的资源，形成了闭环等待（Wait-for Graph 环路，例如事务 A 持有资源 1 等待资源 2，事务 B 持有资源 2 等待资源 1）。此时没有任何一方能主动继续执行，若无外界介入将永久卡死！
- **死锁检测器守护线程（Deadlock Detector）**：DB2 内部运行着独立的后台检测线程。
- **检测频率（DLCHKTIME）**：数据库配置参数 `DLCHKTIME`（Deadlock Check Time，单位毫秒，默认 `10000` 毫秒即 10 秒）。每隔 10 秒检测器唤醒一次，扫描当前的锁等待依赖图（Wait-for Graph）。
- **牺牲者机制（Victim Selection）**：一旦检测到闭环死锁，DB2 会依据事务开销算法挑选一个事务作为“牺牲者”（Victim），主动将其**强制回滚**，从而打破环路，让另一个事务得以顺利继续执行！
- **报错特征**：被牺牲的事务在窗口中捕获到：
  
  ```text
  SQL0911N 因为死锁或超时，当前事务已回滚。原因码 "2"。
  (SQL0911N The current transaction has been rolled back because of a deadlock or timeout. Reason code "2".)
  ```
- **核心辨析（考点重点）**：
  - **死锁（Deadlock）**：双向循环等待，由后台线程在 **极短时间（通常 10 秒内）** 主动打破，报错原因码为 **`2`**；
  - **超时（Timeout）**：单向等待，被动耗尽设定的等待时间（如 90 秒）后放弃，报错原因码为 **`68`**！

### 0.7 Windows XP 多窗口独立会话并发模拟核心技术

在 Windows XP 操作系统下，如何优雅、纯净地模拟多用户事务并发？

- **CLP 体系原理**：在 Windows 平台上，每个新打开的 **DB2 Command Window** 在首次执行 `db2` 命令时，都会在后台衍生一个独立的命令行处理器后台进程 **`db2bp.exe`**！

- **多事务并发本质**：这意味着，即使在同一台机器上使用同一个系统账号打开三个 DB2 Command Window，DB2 引擎也完全将其视作**三个独立的客户端并发连接与独立事务**！
- **窗口角色分工**：
  1. `student` 窗口：模拟前端普通业务查询与事务。
  2. `db2admin` 窗口：模拟后台管理员或并发修改事务。
  3. `monitor` 窗口：专职执行快照监控、配置调优与环境管控。

### 1.12 行锁与表锁的依存关系剖析（意向锁的必要性）

**原题 12. Is there ever a case where a row lock is possessed without a corresponding lock on the table which contains the row?**

**【标准答案】**：

> **No（绝对不会存在这种情况）。**  
> **底层原理解释**：  
> DB2 严格遵循**多粒度层次封锁协议（Multiple Granularity Locking Protocol）**。在任何事务对底层数据行加锁（如行级 X 锁或 S 锁）之前，数据库引擎**必须且强制**首先在其顶层所属的数据表上加上对应的意向锁（如表级 IX 锁或 IS 锁）。  
> 如果允许在没有表级意向锁的情况下直接持有行锁，其他事务若想申请整表的表级排他锁（X）或共享锁（S），就必须逐行遍历表中所有数据行去核查是否存在行锁，这在工程上是不可行的。因此，行锁必定依附于表级意向锁而存在。

> 2. **对象与语义解析（Semantic & Object Validation）**：查询 `SYSIBM.SYSTABLES` 和 `SYSIBM.SYSCOLUMNS`，确认表是否存在、别名是否正确、字段 `itemno` 和 `type` 的数据类型与约束定义；
> 3. **访问路径与执行计划生成**：查询系统统计信息表，决定使用哪个索引。  
>    在读取并缓存这些元数据时，DB2 引擎会对相应的系统目录表施加短暂的共享/意向锁以保障元数据并发一致性。

### 2.2 查询结果与行级锁互不干扰原因分析

**原题 2. What happened and why? (Recall that you currently have a row where itemno = 200 locked by the db2admin application.)**

### 2.4 挂起原因与锁冲突现象深入剖析

**原题 4 (原讲义对应提问). What happened and why? (Recall that you currently have a row where itemno = 200 locked by the db2admin application)**

**【标准答案】**：

> **现象**：`student` 窗口的 SQL 查询命令被**完全阻塞挂起（Blocked in Lock Wait）**。  
> **原因分析**：  
> 此时 `db2admin` 会话在 `itemno = 200` 的数据行上持有着未提交的**排他锁（X 锁）**。当 `student` 会话尝试使用默认的游标稳定性（CS）隔离级别执行 `SELECT` 读取该行数据时，必须首先在该行上获取**共享锁（S 锁）**。依据锁兼容性矩阵，**S 锁与 X 锁完全不兼容**，因此 DB2 锁管理器将 `student` 应用程序置于“锁等待”队列中挂起，等待 `db2admin` 释放该行的 X 锁。

### 2.5 表级锁是否导致争用问题的辨析

**原题 5. Did table locking cause the contention problem?**

**【标准答案】**：

> **No（不是表级锁导致的争用）。**  
> 导致冲突争用的是**行级锁（Row Lock）**，而非表级锁。  
> 在表级别上，`db2admin` 持有的是表级意向排他锁（IX 锁），而 `student` 查询时申请的是表级意向共享锁（IS 锁）。查阅锁兼容性矩阵可知，**表级 IX 锁与表级 IS 锁是完全兼容的**！如果争用源于表锁，那么在第 1 步中查询 `itemno = 198` 时就应当被阻塞。事实证明查询 198 畅通无阻，只有查询 200 时被挂起，充分证明阻塞是目标行上的 **Row X Lock** 与 **Row S Lock** 冲突所致。

### 2.6 默认隔离级别辨析（CS vs UR）

**原题 6. You have not done anything in the lab environment to change the isolation level in the student window. Consider this and your results from the past two SQL statements issued from the student window. If given a choice between Uncommitted Read and Cursor Stability, which one do you think is the default isolation level for the student window?**

**【标准答案】**：

> **默认隔离级别是 Cursor Stability（CS，游标稳定性）。**  
> **论证理由**：  
> 如果默认隔离级别是**未落实读（UR, Uncommitted Read）**，则事务在执行 `SELECT` 读取数据时根本不需要获取行级共享锁（S 锁），它可以直接“脏读”未提交的脏数据页，绝不会被 `db2admin` 的行级 X 锁阻塞！  
> 正是因为当前窗口在读取 `itemno = 200` 时发生了锁等待挂起，证明其必须获取 S 锁且遵循锁相容原则，这完全符合 **游标稳定性（CS）** 的特征。因此 DB2 的默认隔离级别必然是 **CS**。

### 3.3 构造交叉资源依赖的 SQL 执行序列（严格时序操作）

> [!CAUTION]
> **死锁构造时序红线指导**：  
> 死锁必须满足事务交叉等待条件。请严格按照以下步骤顺序操作：
> 
> 1. 先在 `student` 窗口执行 a 步，再在 `db2admin` 窗口执行 b 步；
> 2. 然后在 `student` 窗口中输入 c 步命令，按回车（此时命令挂起！）；
> 3. 紧接着在 `db2admin` 窗口中输入 d 步命令，按回车（死锁环路瞬间闭合！）。

#### 时序执行明细：

1. **Step a【student 窗口】**：
   
   ```cmd
   db2 +c "select * from stock where itemno = 100"
   ```
   
   *(持有 itemno=100 的行级 S 锁)*

2. **Step b【db2admin 窗口】**：
   
   ```cmd
   db2 +c "update student.stock set qty = qty + 1 where itemno = 200"
   ```
   
   *(持有 itemno=200 的行级 X 锁)*

3. **Step c【student 窗口】**：
   
   ```cmd
   db2 +c "select * from stock where itemno = 200"
   ```
   
   *(按回车执行：student 试图获取 200 的 S 锁，但被 db2admin 的 X 锁阻塞，挂起等待！)*

4. **Step d【db2admin 窗口】**：
   
   ```cmd
   db2 +c "update student.stock set qty = qty + 1 where itemno = 100"
   ```
   
   *(按回车执行：db2admin 试图获取 100 的 X 锁，但被 student 的 S 锁阻塞！此时死锁形成！)*

> **【报告截屏要求 3-2】**：

### 3.4 观察死锁发生现象与循环等待成因分析

**原题 4. What did you observe? Why did this occur?**

**【标准答案】**：

> **实测观察现象**：  
> 在 Step d 按下回车后**仅仅过了几秒钟（远低于 90 秒超时设置，通常在 10 秒内）**，其中一个窗口立刻报错终止，弹出：
> 
> ```text
> SQL0911N 因为死锁或超时，当前事务已回滚。原因码 "2"。
> (SQL0911N The current transaction has been rolled back because of a deadlock or timeout. Reason code "2".)
> ```
> 
> 而另一个原本挂起的窗口则瞬间解除阻塞并执行成功！  
> **深入成因分析**：  
> 两个并发事务构成了经典的**循环依赖闭环（Circular Wait / Deadlock）**：
> 
> - `student` 会话持有行 100 的 S 锁，正在申请行 200 的 S 锁（等待 `db2admin` 释放）；
> - `db2admin` 会话持有行 200 的 X 锁，正在申请行 100 的 X 锁（等待 `student` 释放）；  
>   双方互相等待对方释放资源，形成了图论中的有向环路。DB2 死锁检测线程依据 `DLCHKTIME` 在 10 秒内捕获到了该死锁环，主动选择其中一个事务作为牺牲者（Victim）强制回滚（原因码 2），打破了僵局！

### 3.13 宏观总结：dlchktime 与 locktimeout 的工程协同关系

**原题 13. Make a general statement about the relationship of the configuration parameters dlchktime and locktimeout.**

**【标准答案】**：

> **【企业级数据库工程总结】**：
> 
> 1. **职责定位差异**：
>    - `DLCHKTIME`（死锁检查间隔）负责**主动巡检双向或多向的死锁闭环（Deadlock Cycle）**。因为死锁闭环永远不可能自行恢复，必须越快侦测并打破越好，因此该值通常设置得非常短（如 10 秒）；
>    - `LOCKTIMEOUT`（锁超时时限）负责**被动限制单向锁等待的最大容忍时间（Max Lock Wait）**。它允许事务在正常业务排队中合理等待一段时间，只有在超时后才被迫放弃回滚，因此该值通常较长（如 30~90 秒）。
> 2. **协同设计原则**：
>    - 在企业级生产环境中，**`DLCHKTIME` 必须显著小于 `LOCKTIMEOUT`**（通常 `dlchktime << locktimeout`）！
>    - 这样设计能够确保一旦发生致命死锁，数据库后台能够以秒级速度敏捷拆解闭环、恢复高可用，绝不会让互相等待的死锁事务无辜消耗宝贵的 90 秒超时时间，从而最大化系统的并发吞吐量与稳定性。
