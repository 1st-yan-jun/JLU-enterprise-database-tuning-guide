## 0. 实验前环境准备与脚本一键预处理

### 0.1 实验背景与核心知识体系（贴合 Unit 6 PPT）

本实验（Unit 6 Moving Data）是整个 DB2 课程中最精彩、同时也是故障率与技术综合度最高的实验。其核心主线与设计意图在配套课件《Unit 6.pptx》中有深入透彻的阐述：

1. **IMPORT vs LOAD 的本质区别（Slide 6）**：
   - **IMPORT**：本质上是通过 SQL 引擎多次循环执行标准的 `INSERT` 语句。每次插入都要逐行检查外键与检查约束，每行均记录完整的事务日志，会激活已定义的 INSERT 触发器，并发时加行锁或意向排他锁（IX 锁），支持其他并发写操作。优点是安全性高、简单；缺点是海量数据导入速度慢、日志开销极大。
   - **LOAD**：绕过 SQL 编译解析器与约束引擎，直接格式化物理数据页（Data Pages）并以块写入方式高速刷入表空间。仅记录极少量的元数据日志（Minimal Logging），不激活任何触发器，装载过程中不进行外键约束校验。并发时加表级排他锁（X 锁）或只读锁。速度极快，但装载完成后需要通过 `SET INTEGRITY` 命令进行事后完整性校验。
2. **LOAD 的四个阶段（Slide 15-21）**：
   - **Load 阶段**：向表写入物理数据行，收集索引键值；格式不合规的行写入转储文件（Dump-File）。
   - **Build 阶段**：基于收集到的键值建立或更新索引，对索引键排序。
   - **Delete 阶段**：发现违反主键或唯一索引约束（Unique Key）的行，将重复冲突行从目标表中删除，并转存入指定的**例外表（Exception Table）**。
   - **Index Copy 阶段**：将处理完的干净索引页写入磁盘。
3. **表状态与“必须做出不好用”（Slide 25, 29-31）**：
   - 教师课件特别指出：“做实验时，做着做着可能表就不好用了，而且**必须做出不好用**，如果一直好用，就是做错了！”
   - 当使用 `LOAD REPLACE` 将父表 `ARTISTS` 的数据替换（装入比原来少一行的 `ART2.EXP`）后，父表和其关联的子表（`ALBUMS`、`STOCK`）将陷入 **Set Integrity Pending（设置完整性暂挂状态，代码 `SQL0668N 原因码 1`）**。整个实验的下半场就是系统地学习如何利用例外表、`SET INTEGRITY` 命令及数据补全手段，将受损的数据完整性链条彻底修复！

### 1.1 导入 ARTISTS 表（避坑代码页 SQL0332N 与 modified by forcein）

#### 题目要求

使用 IMPORT 实用程序将 `artists.exp` 文件导入到你的 `ARTISTS` 表中。  
指定参数：

- 导入文件名：`artists.exp`
- 文件格式：`ixf`
- 导入模式：`insert`
- 消息文件名：`art.msg`
- 截屏记录操作过程。

#### PPT 考点与核心避坑深度剖析（Slide 11, Slide 40）

课件 Slide 40 特别提示：“**注意，会发生错误。打开选项卡的‘列’，勾上‘忽略代码页不匹配，且不进行转换’。**”  

- **错误成因**：由于操作系统是 Windows 简体中文版（代码页 1386/936），而官方提供的 IXF 文件（`artists.exp`）导出时带有英文代码页 850 标记。DB2 默认会尝试做代码页转换，因缺少 850 ➔ 1386 的直接映射表，会引发报错：
  
  ```text
  SQL0332N 找不到从代码页 "850" 到目标代码页 "1386" 的字符转换。SQLSTATE=57017
  ```
- **完美解决方案**：添加修饰符 `modified by forcein`。该修饰符指示 DB2 忽略代码页不匹配，直接按原始字节流将数据强行写入表中，完美避免转换失败！

#### 执行命令（确保在 CF23 目录下）：

```cmd
db2 "import from artists.exp of ixf modified by forcein messages art.msg insert into lzb_1019.artists"
```

> [!NOTE]
> 如果当前连接会话的模式名已经是 `LZB_1019`，写 `insert into artists` 亦可，推荐显式指定 `lzb_1019.artists` 以示独立归属。

#### 预期终端输出：

```text
SQL3109N  实用程序正在开始从文件 "artists.exp" 装入数据。
SQL3110N  实用程序已完成处理。从输入文件读取了 "79" 行。
SQL3221W  ...（关于 forcein 的信息性警告提示）
SQL3149N  实用程序已完成处理。从输入文件读取了 "79" 行。在目标表中插入了 "79" 行。没有拒绝行。确定了 "79" 行。
```

> **原因解释**：我们在实验 3 中定义的 `REORDER` 触发器其触发事件限定为 `AFTER UPDATE OF QTY`（库存数量被更新时触发）。而本次 IMPORT 采用的是 `INSERT` 模式向空表插入新记录，根本没有发生任何针对现有行的 UPDATE 操作，因此触发事件未被满足，触发器未执行，REORDER 表保持为空。

### 2.2 思考题：例外表命名规范与两额外列（TS 与 MSG）深度解析

#### 题目要求

> Note that the table space SMSEXP is being created to store all of the exception tables. Also note that the exception tables mimic the base table plus two additional columns.  
> What are the exception table names? What are the two additional columns and their attributes? Are they optional?

#### PPT 核心理论剖析（Slide 22, 23, 45）

课件 Slide 22 特别给出《Rules for creating Exception Table》：

1. **前 n 列**：与基础原表的业务列结构完全镜像一致（列名、数据类型、长度相同），但**严禁包含任何约束（主键、外键、CHECK约束等）以及触发器**。
2. **第 n+1 列**：必须是时间戳类型（`TIMESTAMP`），列名通常为 `TS`，用于记录违规记录被捕获并移入例外表的具体时间。
3. **第 n+2 列**：必须是字符型大对象（`CLOB(32K)` 或 `VARCHAR`/`LONG VARCHAR`），列名通常为 `MSG`，用于由 DB2 存储违反约束的具体错误原因代码与消息说明（例如违反了哪一个外键约束）。
4. **是否可选（Are they optional?）**：**不可选（NOT optional）**！DB2 的 `LOAD ... FOR EXCEPTION` 和 `SET INTEGRITY ... FOR EXCEPTION` 底层算法强制依赖这两列记录元数据，缺少任何一列均会导致语法错误或执行拒绝。

#### 报告作答标准答案：

> **1. 例外表名称（Exception Table Names）**：
> 
> - `ARTISTS` 表对应例外表：**`ARTEXP`**
> - `ALBUMS` 表对应例外表：**`ALBEXP`**
> - `STOCK` 表对应例外表：**`STOEXP`**
> 
> **2. 两个附加列及其属性（Two Additional Columns & Attributes）**：
> 
> - **列 1：`TS`**，数据类型为 **`TIMESTAMP`**。作用：记录该违规行被移入例外表的时间戳。
> - **列 2：`MSG`**，数据类型为 **`CLOB(32K)`**。作用：存储该行所违反的完整性约束的具体错误信息与约束标识符。
> 
> **3. 它们是否可选？（Are they optional?）**：
> 
> - **不可选（No, they are NOT optional）**。在 DB2 规范中，例外表的前 n 列必须与基础表列完全一致，且末尾**必须强制包含**这两个附加列用于捕获违规上下文。缺少这两列时，DB2 的 `SET INTEGRITY` 或 `LOAD` 将无法将违规行转储到例外表中。

### 5.2 思考题：FOR EXCEPTION 捕获何种违规？（唯一键冲突）

#### 题目要求

> The LOAD command loads rows into the ARTISTS table using a different IXF input file from the earlier IMPORT. Note that it uses the REPLACE option to replace the previously imported rows in the ARTISTS table. The artexp table is specified to contain exception rows for the ARTISTS table during the load with the FOR EXCEPTION OPTION.  
> What type of violations will be stored in this table during the load?

#### PPT 理论深度剖析（Slide 15, 21, 54）

- **LOAD 阶段的违规分工**：
  - 数据类型不匹配、字段长度超限的非法畸形行，在 **Load 阶段** 被拒并写入 **转储文件（Dump-File）**。
  - **唯一性索引冲突（Unique Key / Primary Key Violations）**：在 **Delete 阶段** 被检测出来。当装载的数据中存在主键或唯一索引键重复的记录时，DB2 会将冲突的冗余行从目标表中删除，并存入通过 `FOR EXCEPTION` 指定的例外表（`ARTEXP`）。
  - **特别注意**：LOAD 过程中**不检查外键参照完整性**！因此外键违规绝对不会在 LOAD 运行期间写入例外表，而是留到后续的 `SET INTEGRITY` 阶段去捕获！

#### 报告作答标准答案：

> **答**：  
> 在 LOAD 执行期间，`ARTEXP` 例外表中将保存**违反唯一性约束（Unique Key Violations）或主键冲突（Primary Key Violations）的重复记录**。  
> **原理剖析**：LOAD 实用程序在执行的第 3 阶段（Delete 阶段）会基于 Build 阶段生成的索引检测唯一键冲突。若数据中包含主键 `ARTNO` 重复的行，冲突行将被移出目标表并写入 `ARTEXP` 中，同时在 `TS` 记录发生时间，在 `MSG` 记录违规原因代码。在 LOAD 阶段不会检查外键约束，外键违规不会进入此时的例外表。

### 6.2 分析 SQL0668N 原因码 1 与解脱方案

#### 题目要求

> What SQL code did you get on the first select statement? Check the meaning of the SQL code using the online help facilities. What action do you need to take to clear this status? Answer question and show your work below by printing screen.

#### PPT 理论深度剖析（Slide 25, 29, 31）

- **返回的错误代码**：**`SQL0668N`**，原因码为 **`1`**（Reason code "1"）。
- **原因码 1 的官方定义**：
  
  > `1: 表处于“设置完整性暂挂（Set Integrity Pending）”状态。未评估表的完整性，并且它可能受到破坏。`
- **为什么会出现这个状态？**
  因为我们刚对父表 `ARTISTS` 进行了 `LOAD REPLACE`。LOAD 装载数据时绕过了 SQL 约束引擎，DB2 无法确保新数据是否满足外键或检查约束。为了保护数据一致性，DB2 自动将该表锁定在暂挂保护状态，禁止任何常规 SELECT 和 DML 操作！
- **解脱方案（Action to take）**：
  必须对处于暂挂状态的表执行带 `IMMEDIATE CHECKED` 选项的 **`SET INTEGRITY`** 语句，让 DB2 重新校验其参照完整性和约束，校验通过后自动清除暂挂状态。

> ```sql
> CREATE TRIGGER REORDER
> AFTER UPDATE OF QTY ON STOCK
> REFERENCING NEW AS N
> FOR EACH ROW
> MODE DB2SQL
> WHEN (N.QTY <= 5)
> INSERT INTO REORDER VALUES (N.ITEMNO, CURRENT TIMESTAMP);
> ```
> 
> **触发条件（Conditions under which the trigger will fire）**：
> 
> 1. **操作类型（Event）**：必须是对 `STOCK` 表执行 **`UPDATE`** 操作；
> 2. **受影响列（Column）**：UPDATE 必须显式涉及 **`QTY`**（库存量）列；
> 3. **触发时机（Time）**：在更新成功应用之后（**`AFTER`**）；
> 4. **粒度（Granularity）**：针对每一行分别求值（**`FOR EACH ROW`**）；
> 5. **谓词条件（WHEN 子句）**：更新后的新库存值必须满足 **`N.QTY <= 5`**。
>    *注：普通的 INSERT、DELETE、或更新除 QTY 外的其他字段、以及将 QTY 更新为大于 5 的数值均绝对不会触发此触发器。*

### 8.4 比较 EMPTYSTOCK 别名与 REORDER 原表查询结果

#### 题目要求

> Previously you created an alias called EMPTYSTOCK for the REORDER table. Does it give the same results as querying directly against REORDER? Answer question and show your work below by printing screen.

db2 "select * from lzb_1019.emptystock"

> **原理剖析**：别名（Alias）是 DB2 中指向底层实际物理表的一个指针或符号名称，它不会创建独立的数据副本，也不占用额外的物理存储空间。当客户端通过别名 `EMPTYSTOCK` 发起查询时，数据库引擎在解析执行计划阶段会自动将其透明解析重定向到底层引用的基表 `REORDER` 上，因此二者的查询结果与语义完全等价。

1. **深刻理解了 IMPORT 与 LOAD 的架构级差异**：IMPORT 基于 SQL 引擎通过标准 INSERT 逐行插入，全面记录事务日志并实时触发检查约束与触发器；而 LOAD 绕过 SQL 引擎直接写入物理数据页，具有极高的吞吐性能与最小化日志特性。同时在实操中攻克了汉化版 Windows 平台下的代码页匹配难题（`SQL0332N`），掌握了利用 `modified by forcein` 进行高效兼容导入的技能。

4. **熟练运用了 db2look 逆向工程工具**：成功导出了包含表空间布局、主外键约束与大对象存储参数的完整 DDL 脚本，并与系统目录表的 DESCRIBE 结构形成了精准映射。整个实验逻辑清晰，数据完整闭环，极大提升了对企业级数据库系统状态管理与性能调优的工程实操能力。
